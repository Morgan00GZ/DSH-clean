# 设计总览

本文说明 DSH-clean 为什么是现在这个形状，以及它怎么工作。

## 1. 形态决策

| 形态 | 能否分发 | 能否按需 | 主要问题 | 结论 |
|---|---|---|---|---|
| DSH 插件 | 差（依赖宿主版本、需安装） | 否（随宿主启动） | 检查器住在被检查对象里；自身往 `.dsh` 写 node_modules 与 `*.bak-<ts>`，制造待清残留 | 不用 |
| 纯 bat / PowerShell | 中 | 是 | 大量文件时慢；无法解析 asar；无结构化状态 | 只做外壳 |
| 纯 skill | 好 | 是 | 没有引擎，每轮靠模型重新推理，最贵且会漂移 | 只做附属 |
| **独立 CLI（Node 单文件）** | **好** | **是** | 无 UI | **采用** |

三条硬理由：

1. **可用性**：本项目要检查的正是「profile 坏了、node_modules 冲突、插件互相干扰」。检查器若寄生在 profile 里，它想测的故障会让它自己加载不了。
2. **可分发**：其他电脑/其他人复用要求解压即用、零依赖、自定位。插件带安装和版本矩阵，做不到。
3. **按需**：不常驻、不定时、不改宿主配置。一个 `.cmd`，几个子命令。

skill 是**主通道**：它在被调用时加载（约 2 KB），负责告诉 agent「什么时候跑、跑哪个参数、读哪一行、怎么把结论压成一句话问人」。技能由 `install` 部署到 `~/.dsh/skills/dsh-clean/`，与引擎解耦——引擎在 `%LOCALAPPDATA%`，仓库只是分发与升级渠道。

不带技能时，工具照常可用（黑窗口）；带技能时，用户的全部操作退化成「在对话框里说一句话」。这是本项目对「不熟命令行的人」最重要的适配：**命令只出现一次（install），之后不再出现。**

### 1.1 引擎不调用大模型

引擎是纯确定性程序：扫描、比对、按规则归类，**不联网、不需要 API Key**。陌生条目的判断交给上层——在 DSH 会话里就是 agent，在只有黑窗口时就是你本人。

三个理由：

1. **密钥不能散**：内置调用意味着每个使用者都要配自己的 Key。
2. **重复付费**：DSH 已经为推理付费，工具再调一次是重复成本。
3. **判断要留痕**：AI 的判断若隐身在工具内部，就无法复盘、无法纠正。让它出现在对话里，理由可读、决定可记。

分工：**引擎看得全、记得住；AI 想得明白；人点头。** 这也是「日常巡检 200–400 token」能成立的原因——工具不消耗推理，只在需要判断时把一小段摘要交给 agent。

## 2. 数据流

每一步都可单独运行、结果落盘，任何一步中断都不丢状态。

~~~
find-dsh  ->  roots.json          发现安装 / 数据 / AppData / 工作区
                     |
                     v
                   scan  ->  inventory.json     (path, size, mtime)
                     |
   knowledge.base.json  (内置经验，随仓库)
   known.json           (本机判例)
   rules.json           (判据阈值)
                     |
                     v
              classify  ->  KEEP / CACHE / RESIDUE / UNKNOWN / LOCKED
                     |
        +------------+-------------+
        |            |             |
        v            v             v
    report.md    plan.json    unknown 队列
                     |
                 (人工裁决 review)
                     |
                     v
                  apply  ->  Windows 回收站
~~~

## 3. 四层处理

### 3.0 范围

不是只查「客户端本体」，而是把**这台机器上跟 DSH 有关的一切**列出清单：

| 类别 | 例子 | 扫多深 |
|---|---|---|
| 安装目录 | `D:\Software\DeepSeek Harness` | 全量 |
| 用户数据 | `~\.dsh`（配置、插件、会话、缓存） | 全量 |
| Electron 数据 | `%APPDATA%\@deepseek-ai` | 全量 |
| 更新缓存 | `%LOCALAPPDATA%\@deepseek-ai*` | 全量 |
| 工作区 | 从 DSH 配置反解出的全部工作区 | 两层（浅扫，不碰项目内部） |
| 疑似相关 | 名字含 dsh/deepseek/harness 且带 DSH 特征文件的目录 | 三层 |

每个根都带 **来源**（注册表 / 默认 / 启动器 / 配置 / 探测）与 **作用**（安装 / 数据 / 缓存 / 工作区），清单直接可读。

### 3.1 发现层（首次运行、或根目录变化时）

按可靠度依次尝试，全部失败才要求手动指定：

| 类别 | 来源 |
|---|---|
| 安装目录 | 注册表卸载项（DisplayName 含 DeepSeek Harness）→ UninstallString 反推；默认位置 `%LOCALAPPDATA%\Programs\DeepSeek Harness`；portable 版标记 |
| 用户数据 | `%USERPROFILE%\.dsh` |
| AppData | `%APPDATA%\@deepseek-ai\dsh-desktop` |
| 更新缓存 | `%LOCALAPPDATA%\@deepseek-ai\dsh-desktop-updater*` |
| 工作区 | 从 DSH 自身配置反解（`tool-management/history-workspaces.json`、会话索引、`memory/workspaces` 目录名） |

结果写入 `roots.json`，每项带 `source`（registry / default / portable / config / manual）与 `confidence`。之后只读表，不再重新发现——除非表中路径消失。

### 3.2 快照层

- 遍历每个 root，记录 `(relpath, size, mtimeMs)`；**不哈希**
- 指纹 `size:mtime`，与上一份 inventory 做 join，得到 `new / changed / gone`
- `node_modules` 照常遍历（它本身就是残留高发区），但按包粒度聚合展示
- 冷启动目标：4 万文件量级 < 10 秒

### 3.3 归类层（三源 + 兜底）

优先级从高到低，先命中先返回：

1. **本机判例** `known.json`：你裁决过的路径，永不重复问
2. **内置知识** `knowledge.base.json`：按名字模式、目录角色、宿主机制名单判定（随仓库分发，陌生机器首跑就有判断力）
3. **结构判据** `rules.json`：孤儿 / 悬空 / 被取代 / 空目录 / 临时备份 / 停滞
4. **都不中 → UNKNOWN**：显式入队，不静默丢弃。第一轮未知，你一句话裁决后进判例库

标签只有五个：`KEEP`、`CACHE`、`RESIDUE`、`UNKNOWN`、`LOCKED`。
归属 `owner`：`host` / `plugin:<name>` / `cache` / `workspace` / `unknown`。

### 3.4 纯净度：推断基线，而不是让用户记一次

「跟刚安装配置完毕的状态比较」如果要求用户先手动拍一次快照，那一次拍到的其实已经是现状——没有意义。所以改成**从文件系统事实推断**：

**客户端安装目录**：安装器把几万个文件写在同一分钟内，所以 mtime 直方图有一个绝对主峰（本机 7,814 个文件 100.0% 落在同一分钟）。主峰时刻就是"安装时刻"，偏离主峰的文件就是安装之后新增或被改过的。主峰占比低于 60% 时判定为"无法推断"，退回规则判定。

**插件包**：不靠时间戳（npm 包内 mtime 是发布者的、pnpm 硬链接又共享 ctime）。改用 pnpm 自己的**文件仓库**当"安装包原件"：

1. **链接数**：pnpm 不复制文件，而是给包内文件链到仓库里的原件。没被动过 → `nlink ≥ 2`；被改过/替换 → 链接断开 → `nlink = 1`。这一步零成本（扫描时本来就要读文件属性）。
2. **查原件**：对 `nlink = 1` 的少数文件算 sha512，去仓库的 `files/xx/<hash>` 里查。查到 = 内容仍是原件（被复制/重写过，如备份）；查不到 = 内容真的变了。
3. **名册对账**：`node_modules` 实况 vs `pnpm-lock.yaml`，报孤儿包（卸载残留）、缺失、版本不符。

本机实测：309 个包 / 27,705 个文件里，只有 2 个文件链接断开，一个是真被改的 `lib/index.js`，另一个是内容与原版一致的 `.bak` 备份。

**插件数据目录**：没有"出厂状态"可言（是运行时产物），只报体积、本次增减、最近写入时间，配合孤儿/停滞判据。

**配置文件**：只列最近改动时间，不算脏——配置本来就会变。

这条设计的意义是：换一台机器、换一次重装，什么都不用准备，直接就能回答"客户端和插件被改过没有"。
